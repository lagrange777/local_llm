# Задание 29: оптимизация локальной LLM

Кейс: короткие ответы по документации codex-chat-cli через готовые чанки и BM25. Поиск и серверная проверка цитат не меняются между профилями. Оптимизируются параметры генерации, представление документов в prompt и выбор локальных весов.

## Запуск

```sh
docker compose up -d --build
```

Чат: http://127.0.0.1:8081. Выберите «Профиль модели»; результаты доступны на http://127.0.0.1:8081/optimization. История сохраняется в браузере, в каждом ответе записываются профиль и модель. Профили 4B Instruct поддерживают только режим без рассуждений; UI отключает переключатель, API отклоняет think=true.

Для подготовки всех моделей эксперимента:

```sh
docker compose -f compose.yaml -f compose.optimization.yaml run --rm --no-deps optimization-init
```

Подготовка скачивает официальные модели Ollama только при отсутствии локальных копий. Имеющаяся qwen3:8b копируется в rag29-baseline-8b без обновления весов. На чистом томе сначала скачивается qwen3:8b; digest такого исходного checkpoint может отличаться от сохранённого эксперимента. После копирования алиасы не заменяются повторным запуском. Веса остаются в томе models, в Git их нет.

Bootstrap имеет доступ к сети для скачивания весов. App и Ollama работают только в runtime с internal:true; облачная генерация отсутствует. Сохранена Linux/NVIDIA конфигурация compose.gpu.yaml; данный эксперимент выполняется на ARM64 CPU Docker Desktop / Apple M1 Pro.

## Профили

Профили заданы в internal/optimization/profiles.go, фактические параметры доступны через GET /api/optimization/profiles и /api/status?profile=....

| ID | Модель | Контекст | Максимум выхода | Prompt |
|---|---|---:|---:|---|
| baseline | текущая 8B Q4_K_M | 8192 | 1024 | точная исходная инструкция |
| optimized-8b | те же веса 8B | 4096 | 384 | инструкция под короткий RAG |
| optimized-8b-t02 | те же веса 8B | 4096 | 384 | temperature=0.2, только калибровка |
| instruct-4b-q8 | Qwen3-4B-Instruct-2507 Q8_0 | 4096 | 384 | оптимизированный |
| instruct-4b-q4 | тот же checkpoint 4B Q4_K_M | 4096 | 384 | оптимизированный |

В основном сравнении think=false, seed=42. Temperature выбирается до контрольного прогона на отдельном наборе documents/optimization-tuning.json. При равном качестве предпочитается 0. Исходная температура baseline всегда 0.

Q4 и Q8 сравниваются внутри одного checkpoint 4B. Сравнение 8B и 4B также меняет размер и версию модели, поэтому различие нельзя приписать одному квантованию. Размер GGUF на диске не равен использованию RAM. Варианты доступны в [официальном реестре Ollama](https://ollama.com/library/qwen3/tags); [карточка Qwen3-4B-Instruct-2507](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507) подтверждает только non-thinking режим.

## Prompt и контекст

Исходный prompt сохранён в internal/rag/prompts/baseline.txt. Оптимизированный — в optimized.txt: ответить на все части вопроса, прямо подтвердить утверждения строками, сохранить отрицания/условия/имена файлов и отказаться при недостаточных доказательствах. Примеры про заявки и AtlasDB вымышленные и не содержат ответов контрольного набора.

Из заголовков prompt убраны длинные chunk_id: модель использует ref S1...S4 и строки, а реальные ID и метаданные присоединяет сервер. Все выбранные тексты передаются полностью, без нового chunking или изменения retrieval. Хеши prompt и источников сохранены в эксперименте.

Проверка JSON и точных строк не является семантическим доказательством: соответствие смысла проверяется при оценке. Плохая структура допускает одну попытку исправления, непроверенный ответ не публикуется.

Бюджет optimized оценивается по UTF-8 байтам, с резервом выходных токенов и накладных расходов сообщений. Это эвристика, не точный токенизатор. Дополнительно фактический prompt_eval_count проверяется перед публикацией: близкий к пределу контекст отклоняется. Необычная токенизация остаётся ограничением. Ошибка length от Ollama не превращается в успешный обрезанный JSON.

Меньший num_ctx сокращает KV-память, но не размер весов. Меньший num_predict лишь ограничивает длинные ответы; он не ускоряет ответы, которые уже заканчиваются раньше лимита. Эффект оценивается измерениями, а не предполагаемым коэффициентом ускорения.

## Измерения

```sh
# Отдельный подбор temperature:
python3 scripts/evaluate-optimization.py --questions documents/optimization-tuning.json --profiles optimized-8b,optimized-8b-t02 --repeats 1 --output artifacts/optimization29-tuning-new

# Основные 10 вопросов, каждый по три раза для четырёх профилей:
python3 scripts/evaluate-optimization.py --output artifacts/optimization29-new

# Продолжение без повторного выполнения сохранённых запросов:
python3 scripts/evaluate-optimization.py --output artifacts/optimization29-new --resume
```

Скрипт проверяет локальный URL, установленные модели, уникальность профилей, digest весов, параметры, хеши prompt/индекса и фактического retrieval. При изменении входов resume запрещён. Результаты сохраняются атомарно после каждого запроса, включая ошибки; завершённость прогона означает выполнение всех попыток, а не успешность всех ответов.

Перед блоком профиля модели выгружаются. Отдельный cold-запрос загружает веса и прогревает первый prompt; файловый кэш ОС не очищается. Основные запросы идут с прогретыми весами, вопросы повторяются внутри блока; последующие вопросы могут требовать нового prefill. Кэш промптов ограничен 512 МиБ во всех профилях. Порядок блоков фиксирован и может давать эффект времени/кэша; скорость Q4 нельзя заранее считать выше Q8.

С интервалом примерно две секунды плюс время самого опроса измеряются:

- cgroup memory.current и working set (current минус inactive_file);
- занятая память гостевой VM (MemTotal минус MemAvailable);
- счётчик OOM;
- на macOS — RSS Docker VM, общая сжатая память и занятый swap;
- footprint процесса Docker VM до/после каждого блока через vmmap.

Пики — максимумы выборок, кратковременные пики могут быть пропущены. memory.current включает файловый кэш; working set считается отдельно. RSS не включает сжатую/выгруженную память, поэтому приводится footprint. Системный swap относится ко всему Mac, его нельзя целиком приписывать модели. Опрос ресурсов создаёт накладные расходы одинаковым способом для всех профилей.

Качество оценивает ассистент Codex по ожиданиям: корректность и полнота 0–2, подтверждение смысла цитатой, правильный/ложный отказ, точность цитат. Ошибки API оцениваются 0/0. Полнота учитывает утверждения ответа, а не дополнительные факты только в карточке источника. Это не независимый человеческий аудит. Контрольные вопросы зафиксированы в documents/rag-questions.json и ранее использовались в задании 28; новый prompt не подбирается по результатам текущего контрольного прогона.

Итоговый профиль выбирается при сохранении качества относительно нового baseline с учётом скорости и памяти. При ухудшении обоснованности ответов сохраняется исходный профиль; выбор настроенной 8B также зависит от измеренного качества. Все результаты и ограничения: [отчёт](artifacts/optimization29/REPORT.md).

## API и конфигурация

POST /api/chat принимает дополнительное поле profile; неизвестные ID отклоняются. Без него используется RAG_PROFILE. Произвольные модели и параметры через запрос не принимаются. Общая очередь, отмена, тайм-ауты и запрет чужого Origin сохранены. Профиль также применяется к режиму без RAG.

GET /api/optimization/models возвращает digest, размер и квантование установленных моделей без запуска генерации. GET /api/optimization/report читает сохранённый отчёт, подключённый в Docker только для чтения. Старое сравнение RAG остаётся доступно на /comparison; scripts/evaluate-rag.py явно выбирает baseline, чтобы настройки задания 29 не меняли эксперимент задания 28.

RAG_PROFILE задаёт профиль по умолчанию; OLLAMA_MODEL — исходные веса 8B (в Docker rag29-baseline-8b); OLLAMA_PROMPT_CACHE_MIB — кэш промптов; OPTIMIZATION_REPORT_PATH — путь к отчёту. Профили 4B используют отдельные подготовленные алиасы. Изменение default-профиля не должно менять исходные 8B веса.

## Итог выбора

По итогам 120 запросов нет профиля, одновременно улучшающего все показатели. Основным оставлен baseline: 15/19 завершённых предметных ответов целиком подтверждены показанными цитатами, ошибок 2/30. У настроенной 8B — 12/18 и 3/30; у 4B Q8 — 7/16 и 5/30; у 4B Q4 — 10/18 и 3/30. Новые параметры и prompt не активируются автоматически вопреки этому результату.

Экономный профиль instruct-4b-q4 доступен для задач с приоритетом памяти: пик working set 3,87 ГиБ против 6,84 ГиБ, скорость вывода 5,01 против 2,96 токена/с. Первые проходы быстрее, но общая медиана полного ответа 39,26 с против 21,03 с: модель часто пишет больше текста и лишние утверждения. Это компромисс ресурсов и надёжности, а не доказанное улучшение всех сторон качества. Сокращённый новый prompt и квантование испытаны, неудачные результаты сохранены.

Пики памяти в итоговом отчёте включают загрузку весов и рабочие запросы; warm-only значения находятся в JSON. Footprint всей Docker VM остаётся отдельной величиной и не обязан уменьшаться вместе с памятью модели. На новом окружении результаты нужно измерить заново.
