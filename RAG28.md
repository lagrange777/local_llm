# Задание 28: локальная LLM + RAG

Приложение использует готовые чанки из SQLite-индекса соседнего проекта `codex-chat-cli` (репозиторий `lagrange777/aichallenge_hw`), локальный BM25 и Ollama `qwen3:8b`. Эмбеддинги не вычисляются, OpenAI API не вызывается. Полнотекстовый поиск — лексический: он не эквивалентен поиску по старым OpenAI-векторам.

## Запуск

```sh
docker compose up -d --build
```

Чат: http://127.0.0.1:8081. По умолчанию включён переключатель **Поиск в документах**. Отключение переключает генерацию в режим без RAG. Завершённые обмены и выбранный режим сохраняются в браузере. В RAG-ответе показаны источники, разделы, chunk_id и раскрываемые точные цитаты. Сравнение доступно по ссылке **Сравнение режимов** и на http://127.0.0.1:8081/comparison.

Индекс включён в Docker-образ; соседний проект для запуска не нужен. Отчёт подключён к приложению только для чтения. Веса модели остаются в постоянном томе. Первый запуск может скачать образы и модель; после подготовки поиск и генерация выполняются в изолированной сети `runtime` с `internal:true`, без доступа к облаку. Для Linux/NVIDIA сохранён `compose.gpu.yaml`; фактическая проверка здесь выполнялась на CPU Docker Desktop / Apple M1 Pro.

## Импорт существующего индекса

```sh
python3 scripts/import-rag.py --index ../codex-chat-cli/artifacts/docindex/index.sqlite
```

Команда открывает SQLite с `mode=ro` и `query_only=ON`. Экспортирует исходные тексты и метаданные обеих стратегий в `documents/chunks.json`: 79 fixed + 143 structured, корпус примерно 35 страниц при 400 словах на страницу. Векторы и embedding_cache не экспортируются. Переразбиения текста нет; исходные ID, границы, section, source, title и content_hash сохраняются. Импорт проверяет хеш текста каждого чанка и неизменность SHA-256 исходного SQLite до/после чтения; экспорт заменяется атомарно.

`origin` содержит репозиторий, путь исходного индекса, SHA-256 SQLite, хеш корпуса, дату индекса и исходную embedding-модель для происхождения данных. При старте приложение повторно проверяет хеши чанков, непустые метаданные, уникальность ID и выбранную стратегию. По умолчанию используется structured. Это замороженная документация соседнего проекта, а не текущая документация `local_llm`.

## Поиск и ответ

1. Вопрос и документы проходят один анализатор: Unicode-слова, нижний регистр, ё → е, стоп-слова, облегчённая нормализация русских окончаний. Числа и идентификаторы с подчёркиваниями сохраняются. Полного морфологического анализа и семантического расширения запроса нет.
2. BM25 считается локально в Go: k1=1.2, b=0.75, IDF=ln(1+(N-df+0.5)/(df+0.5)). Индекс частот строится в памяти при старте из JSON. Для такого корпуса отдельный векторный сервер/SQL-сервис не нужен. Ранжирование при равных оценках использует chunk_id; порядок суммирования терминов фиксирован.
3. Берутся до 10 кандидатов. Фильтр требует IDF-взвешенное покрытие терминов ≥ 0.22 и минимум два совпадения для многотерминового вопроса. Покрытие — эвристика, не вероятность релевантности. Если явно написанное латинское имя/идентификатор отсутствует в корпусе, отбор пустой. Это помогает не угадывать настройки неописанных технологий, но может дать ложный отказ при другом написании имени.
4. После фильтра — до 4 полных чанков, суммарно до 5000 символов. Чанк, не помещающийся в бюджет, пропускается целиком: номера строк остаются привязаны к исходному тексту. Все решения и оценки доступны в retrieval. Параметры проверены на отдельном наборе `documents/rag-calibration.json`, не подбирались по качеству ответов контрольного прогона.
5. Qwen получает текущий вопрос, найденные документы с номерами строк и ограниченную историю (не более 1000 символов). История помогает интерпретации, но не служит доказательством. Retrieval выполняется по текущему вопросу; разрешение сложных местоименных уточнений в отдельный поисковый запрос здесь не реализовано.
6. Модель возвращает JSON с максимум тремя утверждениями и ссылками на строки. Сервер проверяет схему, существование ref, диапазоны и наличие непустой цитаты для каждого утверждения. Цитаты извлекаются из исходного чанка. Один повтор разрешён для исправления структуры/ссылок. Непроверенный ответ не показывается и не попадает в историю. Это проверка точности цитат и структуры, не независимая семантическая проверка утверждений: смысл оценивается в контрольном прогоне.
7. При пустом отборе модель не вызывается: возвращается «Не знаю по доступным документам. Уточните вопрос или добавьте источник с нужной информацией». Модель также может отказаться при наличии неподходящих чанков. Отказ не означает доказанного отсутствия факта во всём корпусе. У отказа нет выдуманных цитат; интерфейс явно показывает отсутствие подтверждённых источников.

Обычный режим показывает ответ потоком. В RAG-режиме итоговый текст появляется после завершения проверки JSON; рассуждения (если включены) идут отдельно. Поэтому время первого внутреннего токена модели отличается от времени первого видимого ответа. Есть остановка, тайм-аут и запрет одновременной генерации. Контекст 8192, максимум 1024 выходных токенов. Бюджет по символам — эвристика, не точный токенизатор; слишком большой RAG-промпт отклоняется.

## Настройки

| Переменная | По умолчанию |
|---|---|
| RAG_STRATEGY | structured (или fixed) |
| RAG_TOP_K_BEFORE | 10 |
| RAG_TOP_K_AFTER | 4 |
| RAG_MIN_COVERAGE | 0.22 |
| RAG_CONTEXT_CHARACTERS | 5000 |
| RAG_INDEX_PATH | documents/chunks.json; в Docker /documents/chunks.json |
| OLLAMA_PROMPT_CACHE_MIB | 512; 0 отключает RAM-кэш промптов, максимум конфигурации 8192 |
| RAG_REPORT_PATH | artifacts/rag28/comparison.json; в Docker /reports/comparison.json |

Менять настройки следует до начала отдельного прогона; для новой конфигурации используйте новый каталог результатов. Порог старого embedding-поиска не переносится на BM25.

## API / CLI

```sh
curl -N http://127.0.0.1:8081/api/chat \
  -H 'Content-Type: application/json' \
  -d '{"messages":[{"role":"user","content":"Как приложение защищает JSON-историю от частичной записи при аварии?"}],"think":false,"rag":true}'

go run ./cmd/rag-search -query 'Как приложение защищает JSON-историю от частичной записи при аварии?'
```

POST `/api/chat`: `rag:true` включает BM25, `rag:false` или отсутствие поля сохраняет обычный режим. События NDJSON: start → retrieval → thinking (опционально) → sources → delta → done; при ошибке — error. `sources.answer` содержит status, утверждения и проверенные цитаты. `retrieval` содержит кандидатов и выбранные чанки, параметры, хеши, время поиска. В done — время запроса, генерации, первого токена модели, загрузки, токены и число попыток. Отказ сервера: attempts=0, tokens=0. GET `/api/rag/search?query=...` выполняет только поиск; `/api/status` показывает модель и состояние индекса; `/api/rag/report` читает сохранённый отчёт.

## Сравнение

```sh
python3 scripts/evaluate-rag.py --output artifacts/rag28-new
# Продолжить прерванный прогон с теми же настройками:
python3 scripts/evaluate-rag.py --output artifacts/rag28-new --resume
# Отдельный новый прогон:
python3 scripts/evaluate-rag.py --output artifacts/rag28-another
```

10 вопросов из задания 24: семь ответимых и три о неописанных настройках. Для каждого сохранены ожидания и источники. Каждый вопрос задаётся без истории три раза с RAG и три раза без него; оба режима используют qwen3:8b, think=false, temperature=0, seed=42, num_ctx=8192, num_predict=1024. Пары режимов повторяются по каждому вопросу; порядок режимов чередуется между повторами. Первые пары q01–q03 собраны в начальном последовательном проходе. Обычный кэш промптов Ollama включён: повторы могут получать ускорение. Системные инструкции различаются необходимым контрактом RAG; этот эксперимент измеряет готовые режимы приложения, а не исключительно эффект дополнительных токенов контекста.

Измеряются успешность завершения, ошибки, повторы исправления ссылок, время поиска/первого токена/видимого ответа/полного ответа и совпадение текстов между повторами. Холодный и прогретый запуск рассматриваются отдельно от основного набора. Качество оценивается ассистентом Codex по ожиданиям и исходным цитатам после просмотра ответов: корректность и полнота, правильный/ложный отказ, подтверждение утверждений цитатами. Совпадение текста не доказывает правильность; три повтора при температуре 0 не доказывают стабильность во всех условиях.

Сохранённые облачные ответы `gpt-5.3-codex` импортированы из `codex-chat-cli/artifacts/rag24/comparison.json` в `documents/cloud-baseline.json` с SHA-256 отчёта и датой. Это исторический ориентир: тогда были OpenAI-эмбеддинги, LLM-реранкер, другие чанки и отдельная семантическая проверка. Время облачного ответа не включает общий поиск и итоговое оценивание. Оно не сравнивается напрямую с полным временем локального запроса; стабильность облачной модели по единственному сохранённому прогону оценить нельзя. Новые облачные вызовы не выполняются.

Итоговые метрики, тексты, оценки ассистента и доказательства: [artifacts/rag28/REPORT.md](artifacts/rag28/REPORT.md).

## Память Docker

Исходный прогон на Docker Desktop с 8 ГиБ RAM выявил OOM runner Ollama при сохранении кэша промптов. В финальном Compose установлен `LLAMA_ARG_CACHE_RAM=512` МиБ через `OLLAMA_PROMPT_CACHE_MIB`. Это параметр дочернего llama-server ([официальный парсер llama.cpp](https://github.com/ggml-org/llama.cpp/blob/master/common/arg.cpp)). Он ограничивает кэш промптов, а не всю память модели. Фактический предел подтверждён логом runtime. Веса Qwen 8B и KV-кэш занимают больше 6 ГиБ: для развёртывания нужен запас памяти; на малой машине стоит выбрать меньшую модель.

Все 60 исходных запросов и оба сбоя сохранены. Повтор q09 после исправления и замеры холодного/прогретого ответа хранятся отдельно; их параметры и времена не смешиваются с исходными метриками.

Для повторной проверки q09 с финальным кэшем:

```sh
python3 scripts/evaluate-rag.py --questions artifacts/rag28/cache-fixed/questions.json --output artifacts/rag28-cache-new
```

`evaluate-rag.py` сохраняет измерения без выставления качества. Для исходного прогона оценки всех ответов находятся в `artifacts/rag28/reviews.json`; `runs_sha256` связывает их с исходными событиями и окружением. Отчёт пересобирается командой `python3 scripts/report-rag.py`. Для нового набора надо просмотреть все ответы, заполнить оценки 0–2 и обоснования по той же схеме; переносить старые оценки на новые ответы нельзя.
